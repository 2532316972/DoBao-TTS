# 预制书（Prefetch Book）功能完整整理与移植指南

> 整理自 DoBao-TTS 项目（Node.js + Express + 原生前端），目标：在其它听书/TTS 项目中复刻同款功能。
> 所有结论均来自源码，标注了 `文件:行号`，便于回查。

---

## 0. 一句话概括

**提前把整本书的正文按「行」切成片段并批量合成音频落盘，再用「文本相似度」把阅读 APP 朗读时传来的句子匹配到已生成的 MP3 上直接返回**；未命中就返回一段内置静音 MP3（静默失败，不打断朗读）。

这是整个功能最重要的设计决策：**它不是"按需合成"，而是"离线预制 + 在线查表"**。

```
┌───────────────────────────── 阅读 APP（Legado/阅读） ─────────────────────────────┐

└───────────────────────────────────────┬───────────────────────────────────────────┘

┌───────────────────────────── 本服务端 ─────────────────────────────────────────────┐
│ ① TTS 配置接口   /api/legado/tts-config-prefab   （生成可导入 APP 的引擎 JSON）     │
│ ② 播放端点       /reader/tts/stream-prefetch     （全局文本匹配，强制预制模式）      │
│                  /reader/tts/stream-txt          （TXT 书专用，带 bookId 限定）      │
│                  /reader/tts/stream?usePrefetch=true|false（实时/预制混合入口）      │
│                                        │                                            │
│                                        ▼  cacheQueryService.findAudioByText()       │
│ ③ 音频索引       data/prefetch/books/<书hash>/chapters/<章hash>/index.json          │
│                                        │                                            │
│ ④ 生成链路       txtPrefabService / prefetchService / parallelPrefetchManager       │
│                  ttsService.generateSpeechWithCookie()                               │
│                                        │                                            │
│ ⑤ 正文来源       data/book-cache/books/<书hash>/chapter_N.json（本地缓存）           │
│                  或 阅读 Web 服务 /getBookContent?url=&index=（网络实时取）           │
```

**两种书籍来源，最终汇入同一套生成链路：**

| 来源 | 入口服务 | 正文获取方式 | 特殊点 |
|---|---|---|---|
| 网络书籍（阅读书城/书架） | `prefetchService`（经 `/legado/prefetch/batch-start`） | 阅读 Web 服务 API 或本地 book-cache | bookId 由 bookUrl 哈希得到 |
| 本地 TXT 文件 | `txtPrefabService`（`/legado/txt-prefab/*`） | 上传即解析落本地缓存，`useCacheOnly: true` | bookId = md5(文件名+前1KB).前16位 |

## 2. 核心原理：为什么"按行切分"能对上

1. **预制阶段**：`processChapter()` 拿到章节正文后，先拼上章节标题，再 `splitTextByNewline()` 按换行切段 → `seg_001, seg_002, ...`，逐段合成 MP3。
   - `src/services/prefetch/prefetchService.js:273-279`（拼标题）、`:826-849`（切分）
2. **朗读阶段**：阅读 APP 也是按段落/行来请求 `speakText` 的，所以请求的文本 ≈ 预制时的某一段原文。
3. **匹配阶段**：`cacheQueryService.findAudioByText()` 归一化文本（去空白/标点、只留中英文数字、转小写）后用 **LCS 最长公共子序列**算相似度：
   - 精确相等 → `1.0`
   - `≥0.95` 直接命中；`≥0.85` 再走变体精确匹配（去空白/去标点/去空白+标点+小写）；`≥ minScore` 仅记日志；否则未命中
   - 阈值：指定 chapterId 时 `0.7`，指定 bookId 时 `0.7`，全局搜索时放宽到 `0.6`
   - `src/services/prefetch/cacheQueryService.js:34-108`、`:119-206`、`:410-477`

> **移植要点 1**：分段规则必须和"客户端请求文本的粒度"一致。本项目踩过的坑：早期会把短行合并成长段，结果阅读 APP 请求"但是"、"……"这种短句时永远匹配不上，于是改成**绝不合并短行**（`prefetchService.js:836-840` 的注释明确记录了这一点）。

> **移植要点 2**：未命中必须返回**合法音频**（静音 MP3），不能返回错误码，否则 APP 会中断朗读。项目里用 base64 硬编码了一个约 1KB 的静音 MP3（`src/routes/legado.js:320`、`:165`、`:2350`）。该素材来自阅读官方对接文档，见 **附录 A.5**。

> **"按行切分"为什么能对上——外部证据**：阅读 Web 服务 `getBookContent` 返回的章节正文，本身就是以 `\n` 分隔的段落串（每段开头还带全角空格 `\u3000`），APP 朗读时正是**逐段**把 `speakText` 送出来。所以"服务端按 `\n` 切"与"APP 按段请求"天然同构——这是整套方案的立足点，也是分段规则不能随便改的根因。原始返回样例见 **附录 A.4**。
> 配套地：`splitTextByNewline` 做 `trim()` 去掉行首尾空白，`normalizeText` 去掉 `\u3000` 与全部标点，两边的噪声被同一套规则消掉。

### 3.3 `getSafeDirName` 规则（`src/utils/pathUtils.js:100-112`）

```js
export function getSafeDirName(name) {
  if (!name) return 'unknown'
  if (isShortHash(name)) return name.toLowerCase()   // /^[a-f0-9]{16}$/i → 幂等
  return md5Hash(name).substring(0, 16)              // md5 前16位
}
```
- 目的：规避 Windows 260 字符路径限制。
- **book-cache 与 prefetch 复用同一函数**，所以两边的书籍目录名天然一致（`bookCacheService.js:347-351`）。

### 5.3 播放命中

```
阅读APP GET /api/reader/tts/stream-prefetch?text=xxx
  → cacheQueryService.findAudioByText(text)         // 不带 bookId → 全局搜索，阈值 0.6
      → findInAllIndexes：遍历 data/prefetch/books/*/chapters/*/index.json
  → 命中且文件存在且 size>0 → sendFile（audio/mpeg + Content-Length）
  → 否则 → 静音 MP3

TXT 书专用：GET /api/reader/tts/stream-txt?text=xxx&bookId=xxx
  → txtPrefabService.findAudioByText → cacheQueryService.findAudioByText(text, bookId)  // 限定书内，阈值 0.7
```

**TTS 配置如何导入 APP**（`public/js/legado-tts.js:1051-1170`）：
- 配置 URL：`{origin}/api/legado/tts-config-prefab?engineName=DoBao-预制模式`
- 一键唤起：`legado://import/httpTTS?src=<encodeURIComponent(configUrl)>`
  - `httpTTS` 是 `legado://import/{path}` 的其中一种 path，完整类型见 **附录 A.1**
- 兜底：复制 JSON 手动导入（无二维码能力）
- 注意：`src` 必须 `encodeURIComponent`，且引擎 JSON 内若含 JS，反斜杠需多重转义（**附录 A.3**）
- 生成的引擎 JSON：
```jsonc
{ "id": <ts>, "name": "DoBao-预制模式",
  "url": "http://host:port/api/reader/tts/stream-prefetch?text={{java.encodeURI(speakText)}}",
  "contentType": "audio/mpeg", "concurrentRate": "1",
  "enabledCookieJar": false, "header": "", "loginUrl": "", "loginUi": "", "loginCheckJs": "",
  "lastUpdateTime": <ts> }
```
- **`concurrentRate` 必须为 `"1"`**（TTS 调用禁止并发）。

## 8. 关键算法（可直接复用的源码）

### 8.1 文本分段（**核心，决定命中率**）— `prefetchService.js:826-849`
```js
splitTextByNewline(content) {
  if (!content) return []
  const normalizedContent = content.replace(/\r\n/g, '\n').replace(/\r/g, '\n')
  const rawSegments = normalizedContent.split('\n')
    .map(seg => seg.trim())
    .filter(seg => seg.length > 0)
  // 注意：不再合并短段落，确保每个段落都能被独立匹配
  // 阅读APP请求的文本可能只包含短段落（如"但是"、"……"等）
  // 如果合并段落，会导致缓存查询无法命中
  const segments = rawSegments
  return segments
}
```
- 无长度上限、不合并短行、过滤空行。
- segmentId：`seg_${String(i+1).padStart(3,'0')}`。

### 8.2 文本归一化与相似度 — `cacheQueryService.js:396-450`
```js
normalizeText(text) {
  return text.replace(/[\s\u3000]+/g, '')
             .replace(/[^一-龥a-zA-Z0-9]/g, '')
             .toLowerCase().trim()
}
calculateMatchScore(t1, t2) {
  if (!t1 || !t2) return 0
  if (t1 === t2) return 1.0
  return this.longestCommonSubsequence(t1, t2) / Math.max(t1.length, t2.length)
}
```
> LCS 是 O(m·n) DP。本项目是"全书遍历 + 逐段 LCS"，**性能瓶颈点**；移植时建议加索引缓存（本项目 60s TTL，`cacheQueryService.js:359-389`）或倒排索引。

### 8.3 TXT 编码识别 — `txtPrefabService.js:106-165`
BOM(UTF-8 / UTF-16LE / UTF-16BE) → 试 UTF-8 → 乱码启发式 `hasGarbledText()`（U+FFFD、连续非 ASCII 字节 + `ÃÂ` 特征）→ 回退 GBK。

### 8.4 TXT 章节识别 — `txtPrefabService.js:189-242`
按优先级匹配 4 类正则：
1. `^第\s*([一二三四五六七八九十百千零\d]+)\s*(章|回|节|卷|篇)\s*[\s:：]?(.*)$`
2. `^Chapter\s*(\d+)\s*[\s:：-]?(.*)$`（忽略大小写）
3. `^(\d+)\s*[、.．]\s*(.+)$`
4. `^第([一二三四五六七八九十百千零\d]+)(章|回|节|卷|篇)\s*[\s:：]?(.*)$`

配套：中文数字转阿拉伯（`chineseToNumber`，`:25-57`）、书名清洗（`extractBookName`，`:172-182`）。
**兜底**：一个章节都没识别到 → 按 5000 字一段硬切，标题 `第N段`（`:293-309`）。

### 8.5 Windows 中文文件名乱码修复 — `legado.js:2214-2219` / `txtPrefabService.js:325-339`
`express-fileupload` 在 Windows 上把 UTF-8 文件名按 Latin1 解码：
```js
const fixedName = Buffer.from(file.name, 'latin1').toString('utf-8')
if (/[\u4e00-\u9fff]/.test(fixedName) && !/[\u4e00-\u9fff]/.test(file.name)) file.name = fixedName
```

## 9. 并发 / 延迟 / 状态机

### 9.1 并发模型
- **章节之间：强制串行**（注释：TTS 调用禁止并发）— `prefetchService.js:496-510, 553-589`
- **段落之间：并行，worker 数 = 有效 Cookie 数** — `parallelPrefetchManager.js:373, 501`
  - 全局共享队列 + 自旋锁（`queueLock`），每轮抢 `1~10` 句（随机，上限 10）
  - 启动分散：`random * 500ms * (i+1)/cookies.length`
  - **段内延迟：6 秒 × [0.8,1.3)**（硬编码，`parallelPrefetchManager.js:163-188`）
  - **批间延迟：`requestDelay` 秒 × [0.8,1.3]**（`:471-484`）
  - 每个 Cookie 固定设备参数 `{deviceId, webId}`，遇 BLOCK 轮换
  - 所有延迟都是"可中断 sleep"（50ms/100ms 轮询 `taskStopFlag`）
- 与实时 TTS 互斥：`cookieManager.acquireCookieLock(cookieId)`（`ttsService.js:1332`）

### 9.2 状态机
- 任务：`pending → processing → paused ⇄ processing → completed / partial / failed`
  - **取消不是 cancelled，而是置 `paused`**（`prefetchService.js:1694`）
  - 启动自愈：`loadExistingTasks` 把遗留的 `processing` 改 `paused`，章节 `processing` 改 `pending`（`:100-131`）
- 暂停：`parallelPrefetchManager.stop(false)` 允许当前批次跑完；章节循环入口检查 `task.status === 'paused'` 抛 `'任务已暂停'`；`processSingleChapter` 捕获后把章节回退 `pending`（`:650-659`）
- 恢复：只重跑 `pending / failed / partial` 章节（`:496-509`）
- 重试：`retryTask()` 对 `failed` 章节以 `forceRegenerate: true` 重跑（`:1730-1789`）

### 9.3 断点续传（三重）
1. 进入并行前：`index.json` 标记有音频 且 `fs.stat().size > 0` 且无 error → 跳过（`:974-992`）
2. 构建 `pendingSegments`：只放"无音频或有 error"的段（`:1013-1032`）
3. worker 内部：每段 TTS 前再 `fs.stat` 一次（`:97-140, 192-212`）
4. 兜底：`saveProgressiveIndex` 落盘前先 `syncAudioFilesToIndex()` 扫描磁盘，把 `.mp3/.aac/.wav/.m4a` 回填进索引，`.aac` 自动转 mp3（`prefetchService.js:1301-1405`）

### 9.4 定时预制
- 调度：`setInterval(checkDueTasks, 60_000)` 的**分钟级轮询**，非 cron（`scheduledPrefetchService.js:172-182`）
- 全局串行：任一任务有 `currentPrefetchTaskId` 直接 return；另扫 `prefetchService.processingTasks` 避免与手动任务撞车（软检查）
- 游标推进：`startIndex = lastChapterIndex + 1`，`endIndex = min(startIndex + chaptersPerRun - 1, totalChapters - 1)`（`:301-302`）；到底自动 `enabled=false`
- 完成后：`waitForPrefetchTaskCompletion()` 每 5s 轮询、最长 1 小时；**下次间隔从"预制完成时刻"起算**（`:381-437`）
- 启动自愈 `fixStuckTasks()`（`:50-84`）；关闭钩子 `pauseAllTasks()`（`server.js:617-644`）

## 12. 已知缺陷与避坑清单（移植时请直接绕开）

**功能性 Bug**
1. `prefetchService.js:1785` 调用了**未定义的** `this.updateTaskProgress` → `retryTask` 结尾必 TypeError。
2. `prefetchService.js:54` 的 `this.processingSegments` **只有 get 没有 set** → 暂停时"等待当前段完成"逻辑永不生效，暂停其实是"跑完当前批"。
3. **`options.speed` 在预制链路完全无效**：一路传到 `generateAudioBatchWithProgressiveIndex` 后只进日志，实际调 TTS 时 `rate: 0` 硬编码（`parallelPrefetchManager.js:230`）。若你的项目要支持语速，必须自己把 speed 传下去。
4. `parallelPrefetchManager` 是**单例且 `stop()` 无 taskId 维度** → 暂停/取消任一任务会波及所有并行中的任务。
5. `batchProcessChapters` 复用暂停任务时，只要有一个 chapterId 重叠就复用旧任务，**不会合并新章节**；且 `newChapterIds`（:422）是死代码。
6. `saveProgressiveIndex` 每次把 `metadata.createdAt` 重置为当前时间（:1443），未沿用首次创建时间。
7. `parallelPrefetchManager.js:271-293` 的 BLOCK 重试用 `i--` **无次数上限**，持续 BLOCK 会死循环。
8. `frontend` `importTxtPrefabToLegado()` 在 `legado-tts.js:1106` 被调用但**全仓无定义** → TXT 来源点"一键导入"必抛错。

**设计层面**
9. 全局文本匹配是 **O(书籍数 × 章节数 × 段数 × LCS)**，书多了会明显变慢；建议按 bookId/chapterId 收敛，或做倒排索引。
10. `index.json` 里存了**完整正文** `content`，大书会显著膨胀磁盘（但换来了可重新分段与追溯，是取舍）。
11. `segments` 的 `totalDuration` 恒为 0（未实现时长统计）。
12. 数据导出**遗漏** `data/scheduled-prefetch/*`、`data/prefetch/tasks/` → 导入后定时预制任务与任务索引不恢复。
13. 移动端 CSS（`mobile-fix.css:869-1010`）的类名与 JS 实际生成的类名不匹配（`.prefab-book-card` vs `.prefab-book`），规则不生效。
14. 无任何预制相关单元测试（全仓仅 `userStatsService.test.js`，且 `package.json` 无 `test` 脚本）。

**易错的环境坑**
15. Windows 中文文件名（见 8.5）。
16. Windows 260 字符路径限制 → 必须用哈希目录名。
17. 阅读 APP 可能丢失 URL 查询参数 → 不要用 `?usePrefetch=true` 这种开关，改用**专用端点**（`stream-prefetch`），本项目正是为此加的。
18. TTS 引擎 `concurrentRate` 必须是 `"1"`。

### A.3 网络 TTS 引擎契约（**核心，必须遵守**）

| `concurrentRate` | 并发数。官方示例给 `"5"`，**本项目强制 `"1"`**（账号限速 + 任务串行），属刻意偏离 |
| `enabledCookieJar` | 一般 `false` |
| `id` / `name` / `lastUpdateTime` | 标识与展示 |
| `header` / `loginUrl` / `loginUi` / `loginCheckJs` | 登录态相关，本项目留空 |

**APP 内置变量（只有这两个是实时生效的）：**
- `{{speakText}}`：朗读文本
- `{{speakSpeed}}`：**语速，范围 5–50**

> 这条解释了预制模式的一个重要约束：`speakSpeed` 是 APP 侧的**实时**变量，而预制音频是离线固化的，二者语义冲突——所以预制模式的 TTS url **刻意不带 `speed` 参数**（`legado.js:118`），语速只能在预制任务启动时定死。本项目前端滑块用的 -50~100 与 APP 的 5~50 是两套量纲，互不通用。

**踩坑提示（来自官方文档）：**
- 引擎 JSON 中的 JS，反斜杠 `\` 需多重转义为 `\\`（JSON 解析会吃掉一层）
- 从网页生成 url 导入时，需手动删掉 `.replace(/\\/g, '')`，否则 JS 执行失败
- 想拿书籍信息等更多变量，只能走 Web 服务方式，url 变量拿不到

**本项目 url 模板对照：**
```
实时：  /api/reader/tts/stream?text={{java.encodeURI(speakText)}}&speed={{speakSpeed}}&voice=xxx&usePrefetch=false
预制：  /api/reader/tts/stream-prefetch?text={{java.encodeURI(speakText)}}
TXT书： /api/reader/tts/stream-txt?text={{java.encodeURI(speakText)}}&bookId=xxx
```
